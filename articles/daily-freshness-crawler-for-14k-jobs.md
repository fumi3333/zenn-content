リゾートソートは、派遣会社6社のリゾートバイト求人を横断で検索できるサイトです。約14,000件を1つにまとめて、時給順に並べ替えられます。個人で作っています。

このサイトが成り立つ条件はひとつで、載っている求人がまだ生きていることです。募集終了したものが並んでいると、横断検索として無価値になります。なので掲載中の全件を毎日1回ずつ確認しています。

その仕組みの話を書きます。相手のサーバーを借りている以上、速く回すことより約束を破らないことのほうが難しく、コードの大半はそちらに使いました。

結論を先に書きます。

- 同じ会社への連続リクエストは1.5秒空ける。この制約がある以上、同じ会社に対する並列化は1秒も速くならない
- GitHub Actionsの55分制限では全件を回りきれず、Azureの無料VMへ移した
- 「1日あたり何件まで叩くか」の計算は1か所に集約した。2か所に書いていたときは違う答えを出していた
- 取得に失敗したページを募集終了と判定しないための安全装置を3重に入れた
- 一番多い障害は例外ではなく、成功と表示されたまま何もしていない状態だった

## 全体の流れ

```
03:00 JST  Azure VM (Standard_B2ats_v2)
           新着の取り込み → 全件の生死確認（約2時間）→ 生データを退避 → push
              ↓
06:30 JST  GitHub Actions
           静的サイトを生成 → 配信先へ配置 → 本番反映 → 日次レポート送信
```

巡回とビルドを別の場所に分けています。理由は次に書きます。

## Actionsでは回りきらなかった

もともと全部GitHub Actionsでやっていました。1日4回、55分の予算を切って少しずつ回す形です。

これが回りきりませんでした。24時間以内に確認できていた求人は、実測で全体の19.2%でした。残りは何日も前の状態のまま「掲載中」として表示されていたことになります。

原因は単純で、時間が足りません。同じ会社への間隔を1.5秒空けると、55分で叩けるのは理論上2,200件です。実際は応答待ちがあるのでもっと減ります。在庫は14,000件あるので、どう割っても1日では一周しません。

さらにGitHub Freeのプライベートリポジトリは月2,000分です。1日4回55分なら月6,840分で、そもそも3.4倍超過しています。無料枠の中で毎日一周する組み方が存在しません。

そこでAzure for Studentsの無料VMへ移しました。B1sは日本東リージョンで在庫が無く`SkuNotAvailable`になったので、同じく無料枠対象のB2ats_v2を使っています。

時間制限が無くなったので、分割をやめて1回で全件を回す形にしました。

```
A社  在庫 4,629  一周 24.0時間
B社  在庫 3,942  一周 24.0時間
C社  在庫 2,823  一周 24.0時間
D社  在庫 1,198  一周 24.0時間
E社  在庫   502  一周 24.0時間
   全社が24時間以内に一周します
```

鮮度は19.2%から97.1%になりました。

## 同じ会社に並列は効かない

設計上いちばん効いたのはここでした。

守っているのは「同じ会社への連続したリクエストの間を1.5秒空ける」という制約で、会社ごとにロックを持っています。会社が違えば同時に叩いて構いません。

この形だと、同じ会社に何本ワーカーを立てても速くなりません。全員が同じ1.5秒の列に並ぶだけだからです。全体の所要時間はこの式で決まります。

```
一番在庫の大きい会社の件数 × 1.5秒
= 3,942件 × 1.5秒 = 約98分
```

最初はこれを理解しておらず、1社を350件ずつのチャンクに割って8並列で流していました。結果、同じ会社のチャンクが先頭に固まって、8本中7本がロック待ちで止まっていました。実効並列は1.5社です。1社1タスクに直しただけで、35件/分から200件/分になりました。

もうひとつ、`fetch()`をロックの内側で呼んでいたのも効いていました。

```python
# 誤：ロックを1.5秒＋応答待ち（0.9〜2.2秒）のあいだ握り続ける
with lock:
    wait_for_interval()
    status, html = fetch(url)

# 正：ロックは間隔の確保だけに使い、通信の間は手放す
with lock:
    wait_for_interval()
status, html = fetch(url)
```

ロックは順番待ちのためのものであって、通信中に握り続ける必要はありません。コードを読まない方向けに書くと、「1.5秒に1回だけ通す改札」を作ったつもりが、改札の中で買い物まで済ませていた、という話です。

## 約束した数字をコードが超えられないようにする

各社には事前に連絡して、最小間隔と1日あたりの上限件数を書面で伝えてあります。

```python
# 会社ごとに、書面で伝えた1日あたりの上限を持つ
# （実際の値は各社との取り決めなので伏せます）
DECLARED_DAILY_CAP = {
    "A社": 5000,
    "B社": 2000,
}
```

この上限を人間の注意力ではなくコードで守りたかったのですが、素直に書くと何度も破りました。原因はいつも計算の順番です。

```python
# 上限を掛けた後に余白や予約枠を足すと、当然超える
cap = min(want, declared_cap)
cap = int(cap * 1.05)          # ここで上限を超える
cap += NEW_FETCH_RESERVE       # さらに超過
```

正しくは、先に予約ぶんを引いてから割り、上限は必ず最後に掛けます。

```python
for key, daily in DECLARED_DAILY_CAP.items():
    if key in agency:
        # 新着取得ぶんとカナリアぶんを先に取り置いてから割る
        cap = min(cap, (daily - NEW_FETCH_RESERVE_PER_DAY) // runs
                  - CANARY_PER_RUN)
```

この順番を3回間違えました。1回目は1.05倍の余白、2回目は新着取得の予約枠、3回目は動作確認用の3件です。超過が12件でも、相手に伝えた数字を超えるという意味では同じ重さだと思っています。

さらに厄介だったのは、この計算を巡回する側と検算する側の2か所に書いていたことです。設定を変えたときに検算ツールだけ古い式が残り、「5,150件」と「5,348件」ほどの違う答えを出していました。書面の数字を検算する道具が実際と違う数字を返すのは、検算していないより悪いです。いまは`plan_caps()`一本にして、検算ツールもそこを呼びます。

```python
sys.path.insert(0, str(ROOT / "tools"))
import daily_refresh as dr
caps = dr.plan_caps(alive, runs, dr.TARGET_SWEEPS_PER_DAY,
                    budget_min, sleep)
```

送る文書の数字も、文章から読むのではなく出典から作り直して突き合わせ、上限を超える計画になっていればその場で異常終了します。

## 生きている求人を殺さないための安全装置

一番怖いのは、取得に失敗したページを募集終了と判定することです。相手のIPブロックやネットワーク障害が起きた瞬間に、生きている求人が大量に消えます。

3段構えにしました。

```python
# 1) HTTP 200 以外は、状態を一切変更しない
# 2) 求人ページらしさの検査に通らない本文は変更しない
LOOKS_LIKE_JOB = re.compile(r"(JobPosting|時給|給与|勤務地|募集|求人)")
# 3) 1回で「終了」に変わる割合が上限を超えたら、結果ごと捨てる
MAX_CLOSE_RATIO = 0.70
```

3番目は、まとめて誤判定するくらいなら何もしないほうがマシだという考え方です。まだ発動したことはありませんが、発動するときは事故のときなので置いています。

加えて、会社ごとに見本を置いています。直近に生きていると確認できた求人を3件だけ先に叩き、全部が判定不能ならその会社の巡回を丸ごと中止します。404は無視します。本当に消えた可能性があるからです。

## 捨てていた情報を残す

生死の判定と同時に、前回と値が違っていれば差分を記録しています。

```json
{"id":"xxxxx-11934","agency":"A社","prefecture":"北海道",
 "job_category":"清掃・ハウスキーパー","field":"wage",
 "from":1100,"to":1140,"at":"2026-09-20T19:16:59+00:00"}
```

追記のみのJSON Lines（`data/history/YYYY-MM.jsonl`）に書いて、一度書いた行は書き換えません。取り直しがきかないからです。求人が消えたあとに「その求人の時給はいくらだったか」を調べる方法はありません。その瞬間に写しておかないと永遠に失われます。

同じ考えで、VM側では`~/archive/YYYY-MM/`にgzipで生データを退避しています。gitとは独立した経路なので、リポジトリが壊れても肥大しても残ります。

読み出し側でも1つやらかしています。記録は`from`と`to`で持っているのに、集計側が`prev_wage_min`という存在しないキーを見ていて、日次レポートがずっと「時給が上がった求人 0件」と出していました。実際は1,040件でした。存在しないキーを`.get()`で引くとNoneが返るだけで、例外は出ません。

## 一番多い障害は例外ではなかった

ここまで書いた事故のうち、プログラムが落ちて気づいたものは1つもありません。全部「成功と表示されたまま、実際には何もしていない」形でした。

YAMLの行継続の直後にコメントを置いたことがあります。

```yaml
run: |
  python tools/daily_refresh.py \
  # 1日の上限
  --limit 3100 --sleep 1.5
```

シェルからは`python tools/daily_refresh.py # 1日の上限 --limit 3100 --sleep 1.5`に見えます。`#`以降が全部消えるので、`--sleep`が既定の0.6秒に落ちました。書面で1.5秒と伝えている相手を0.6秒で叩いていたことになります。YAMLとしては正しいので構文検査では見つかりません。

cronの文字列を変えて参照側を直し忘れたこともあります。`if: github.event.schedule == '0 20 * * *'`のようにスケジュールを比較しているステップがあると、cronを変えた瞬間にそのステップは永久にスキップされます。ジョブは緑のまま、そのステップだけが何もしません。

この2つは専用の検査を書いて、巡回の前に必ず通すようにしました。

```python
if line.rstrip().endswith(BACKSLASH) and lines[i + 1].strip().startswith("#"):
    out.append(f"{path.name}:{i + 2}  行継続の直後がコメント。以降の引数が無効になります")
```

タイムゾーンでもやりました。VMのcronが起動したあとにシステムのタイムゾーンをJSTへ変えたため、cronはUTCを握ったままでした。`0 3`が03:00 UTC、つまり日本時間の正午として登録されていて、毎朝3時の巡回は一度も動いていませんでした。1分ごとに動くテストジョブを仕込んで初めて分かりました。

除外オプションが半分しか効いていなかったこともあります。その日すでに上限まで叩いた会社を外すフラグを足したのですが、計画の計算からは外していたのに、対象を選ぶ関数に渡し忘れていました。上限の設定が無い会社は制限なしで全件が選ばれます。画面には「この会社を外します」と正しく表示され、その数行下に、除外したはずの会社が4,000件近く出ていました。

共通しているのは、緑になったことや自己申告の行を成功の根拠にしていたことです。いまは、その回に何をしたかを実績ファイルに書き出して、そこだけを見るようにしています。

```json
{"対象に選んだ": 13094, "確認できた": 13094, "終了": 1737,
 "募集中": 11002, "失敗": 3, "並行数": 5, "打ち切り": false}
```

以前は日次レポートが、累計の件数を「本日の確認件数」として報告していました。2,000件しか確認できていない日に「13,976件」と届いていたので、鮮度が19.2%まで落ちていることに気づけませんでした。数字が毎日届いていたぶん、かえって安心していたことになります。

## まだできていないこと

新着の取り込みが弱いままです。6社のうち2社はサイトマップもAPIも無く、一覧ページもページ番号がサーバー側で無視されるため、一覧からは辿れません。いまはIDが連番であることを使って、手元の最大IDより上を順に叩いて探しています。歯抜けがあるので、一定数連続で404が続いたらそこを上限とみなして止めます。取りこぼしの可能性は残っています。

寮費の実額も取れていません。公開情報から安全に抽出できたのは全体の0.1%程度で、「寮費無料」と書いてあっても水道光熱費や食費が別のことがあります。ここが取れると実質手取りで並べられるのですが、推測で数字を出すよりはやらないほうがいいと判断しています。

そして、毎朝3時の自動実行がタイムゾーンの件を直したあと、まだ一度も完走していません。部品はそれぞれ動くことを確認しましたが、繋がった状態での完走は明朝が初回です。この記事を書いている時点では、そこは未検証です。

冒頭に書いた「載っている求人がまだ生きていること」という条件は、鮮度97.1%という数字の上ではほぼ満たせました。ただ、それを毎日自動で維持できるかどうかは明日の朝にならないと分かりません。速く回す工夫よりも、約束を破らないことと、静かに壊れたまま緑を出さないことのほうに時間がかかる、というのがここまでの実感です。
