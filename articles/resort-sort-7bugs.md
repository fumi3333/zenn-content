リゾートバイトの求人を派遣会社6社から集めて、時給・寮・食事・勤務期間を同じ基準に揃えて比較できるサイトを1人で作っています。掲載は12,870件、公開ページは163枚です。

https://fumiproject.dev/resort/

この記事は、ある1日にこのサイトで見つかったバグを、直した順にそのまま書いたものです。成功した設計の話ではありません。**動いているように見えて壊れていたもの**の記録です。

なぜこれを書くかというと、求人データを扱うサイトは「たくさん集めました」「高速です」と言うのは簡単で、実際に信用できるかどうかは**壊れたときに気づける作りになっているか**でしか判断できないと思っているからです。自分のサイトについてそれを示すには、壊れた実例を出すのが一番早い。

先に結論です。

- 画面上は正常に見えるのに壊れている、が繰り返し起きた
- 共通しているのは「**失敗が成功として扱われていた**」こと
- 検査を自動化していなければ、どれも見つからなかった

## 1. 本番の内部リンクが163ページ全滅していた

一番大きいものから。ある時点で、サイト内のリンクが全部こうなっていました。

```
https://fumiproject.dev/resort/resort/about/   → 404
https://fumiproject.dev/resort/resort/age/     → 404
```

`/resort/` が二重になっています。原因は、ページ生成側が `href="/resort/..."` を直接書くようになったのに、配置スクリプトが**そこへもう一度** `/resort/` を足していたことでした。

```python
# 配置時にルート相対リンクを書き換える
text = re.sub(r'href=(["\'])/(?!/)', lambda m: f'href={m.group(1)}/{GENRE}/', text)
```

正規表現は `/` で始まるものを全部拾うので、すでに `/resort/` が付いているものも拾います。

**厄介なのは、画面上は普通に動いていたこと**です。Vercel 側に保険のリダイレクト設定があり、`/resort/resort/about/` が 308 で正しい場所へ飛んでいました。人間が触る限り、何も起きていないように見えます。

見つけたのはリンク検査スクリプトでした。サイトマップに載っているURLと、全ページのリンク先を実際に叩いて確かめるだけのものです。

```
===== 検出した不整合 合計 224 件 =====
```

自分の手元では0件でした。ローカルのHTMLを見て「hrefの形は正しい」と判断していたからです。**書き換えが二重にかかるのは配置のときなので、配置後の実物を叩かないと分かりません。**

修正は、すでに付いているものを除外するだけです。

```python
text = re.sub(r'href=(["\'])/(?!/|resort/)', ...)
```

教訓としては、**自分のローカル確認より、本番を叩く検査を信じる**。これに尽きます。

## 2. Googleに、2つ前のドメインのURLを毎日申告していた

このサイトは短期間にドメインを2回移しています。

```
resort-sort.fumiproject.dev  →  sort.fumiproject.dev/resort/  →  fumiproject.dev/resort/
```

旧ドメインからは 308（恒久リダイレクト）を返していたので、統合されるはずでした。ところが Search Console を見ると、いつまでも旧ドメインが検索結果に出ます。

調べたら、**サイトマップに載っている163件のURLが全部、2つ前のドメインのまま**でした。

```xml
<loc>https://resort-sort.fumiproject.dev/worry/short/</loc>
```

配置スクリプトはHTMLもXMLも書き換える設定になっていたので、コードとしては正しい。ではなぜか。**別の作業で、生成物が配置スクリプトを通さずに直接コピーされていた**からです。

つまり自分で、古いURLを毎日Googleに申告し続けて、旧ドメインを生かしていました。統合されないのは当然です。

これも画面上は完全に正常でした。リダイレクトが効くので。

## 3. 「おすすめ順」が、絞り込んだ瞬間だけ別の順番になっていた

並び順のスコアが、サーバー側（Python）とブラウザ側（JavaScript）の2か所に書いてありました。

```javascript
const PARTNERS = ["グッドマン", "スタッフエージェント", "RESORT CROSS"];
```

こちらだけ古いままで、あとから追加した2社が入っていませんでした。

**最初に表示される100件はサーバー側が並べたもの**なので正しく出ます。利用者が絞り込みを1回でも触った瞬間に、ブラウザ側が並べ直して順番が変わります。見ていて気づける類のズレではありません。

直し方は、2か所に書くのをやめることでした。

```python
html = html.replace("__PARTNERS__", json.dumps(sorted(A8_DEEPLINK), ensure_ascii=False))
```

**同じ意味の値を2か所に書いたら、いつか必ず片方だけ古くなります。**このサイトでは3回目でした。

## 4. 自動更新が3日連続で失敗していたのに、誰も気づけなかった

毎朝、掲載中の求人がまだ募集しているかを確認して、終了したものを落とす処理が動いています。GitHub Actions です。

実行履歴を見たら、こうでした。

```
09-17  failure
09-16  failure
09-16  failure
09-15  success
```

原因はログにありました。

```
FileNotFoundError: [Errno 2] No such file or directory: 'c:\resort-sort\jobs.json'
```

Windowsの絶対パスがコードに残っていました。手元では動き、CIでだけ落ちます。**このプロジェクトで2回目**です。

そして本題はここからです。**なぜ3日も気づかなかったか。**

失敗を知らせるメールを送るステップは入っていました。ログを見るとこうです。

```
[INFO] SMTP_USER / SMTP_PASS が未設定のため、ログ出力のみ完了しました。
```

通知の仕組みはあるのに、資格情報が設定されておらず、**一度も送信されていませんでした。**しかもその処理は `|| echo "..."` で失敗を握りつぶしていたので、通知が飛ばないこと自体もエラーになりません。

毎朝動く処理は、止まっても画面に何も出ません。**「失敗したときに気づく経路」が動いていることを確かめない限り、無いのと同じです。**

## 5. 5日前のデータで計算した結果を、本番に出していた

同じワークフローの中に、会社をまたいだ時給差を計算する処理があります。この順番でした。

```
1. 求人の生死を確認
2. 時給差を計算      ← public/jobs.json を読む
3. サイトを生成      ← public/jobs.json を作る
```

**2 が 3 より前にあります。**その時点で `public/jobs.json` はまだ存在しないので、フォールバックとしてリポジトリに残っている古い `jobs.json` を読んでいました。

```
読んでいたデータ： 2026-09-13 時点  10,291件
実際の掲載　　　： 12,870件
```

5日前・2,573件少ないデータで時給差を計算し、その結果を本番に載せていました。エラーは一切出ません。フォールバックが「ちゃんと」動いているからです。

**フォールバックは、静かに間違った答えを返す仕組みでもあります。**

## 6. 受け取れないのに、メールアドレスを集めていた

検索結果が0件だったとき、「新着が出たらお知らせします」というフォームが出るようにしていました。画面にはこう書いてありました。

> 新着求人が大手各社から追加され次第、最速でお知らせできます（完全無料・通知はいつでも解除可）

受け口を実際に叩いてみました。

```
POST https://…workers.dev/alerts  →  200 "ok"
```

一見、成功しています。しかし `/alerts` の経路は**まだ実装されていません**でした。同じWorkerにある別の受け口（アクセスログ用）が、知らないパスのPOSTにも `ok` を返していたのです。

つまり、**利用者はメールアドレスを入力でき、それはどこにも保存されず、永久に何も届かない。**保存していないので、後から謝ることもできません。

登録の受付自体を止めました。あわせて、失敗時のメッセージが「ネットワークをご確認ください」と利用者のせいにしていたので、「こちらの不具合です」に変えました。

**「200が返ってきた」は「意図した処理が行われた」ではありません。**

## 7. サイトマップが、存在しないページを申告していた

同じ仕組みで作っている別ジャンルのサイトを検査したら、こうでした。

```
sitemap.xml の 292URL のうち、実体が無いもの 7
   /pref/kanagawa/  /pref/kyoto/  /pref/nara/ …
```

データが無くてページを作らなかった県が、サイトマップには残っていました。Googleに「ここにページがあります」と毎日申告して、毎日404を返していたことになります。

## 共通していること

7件を並べて気づいたのは、全部同じ形をしていることです。

| 何が起きたか | なぜ気づけなかったか |
|---|---|
| 内部リンクが二重 | リダイレクトで動いてしまう |
| 旧ドメインを申告 | リダイレクトで動いてしまう |
| 並び順が2か所 | 初期表示は正しい |
| CIが3日失敗 | 通知が設定されていない |
| 5日前のデータ | フォールバックが動く |
| 届かないフォーム | 別の受け口が200を返す |
| 404を申告 | 人は sitemap.xml を見ない |

**どれも「失敗が成功として扱われていた」**という一点で共通しています。例外は飛ばず、画面は正常で、HTTPステータスは200です。

だから、見つけたのは全部これでした。

- **本番を実際に叩く検査**（リンク・サイトマップ・リダイレクト先）
- **実装と表示を突き合わせる検査**（件数が生成側と画面側で一致するか）
- **CIの実行履歴を人が見る**

言い換えると、**テストが通ったことは品質の証拠になりません。**テストを書いたのも実装したのも同じ人間なので、思いつかなかった経路は最初からテストにありません。上の7件は1件もユニットテストに引っかかっていません。

## いま入れている検査

同じことを繰り返さないために、今は毎回これを通しています。

```bash
python build_public.py && python migrate_to_apex.py && python check_live.py
```

`check_live.py` は本番のURLを実際に叩いて、サイトマップの申告と実体、全ページのリンク先を突き合わせます。遅いですが、上の7件のうち3件はこれが見つけました。

配置の前には、生成されたページ数が不自然に減っていないかを確かめます。

```bash
python tools/guard_page_count.py --src public --dst ../配置先 --allow-drop 3
```

**「ページが減った」は、たいていビルドの失敗が形を変えたものです。**実際に、依存パッケージの入れ忘れで1ページだけ生成されず、それが配置先から「削除」として反映される、という事故が起きています。しかもその依存を書いたファイルには、まさにその事故を警告するコメントが自分で書いてありました。

```
# CIで入れ忘れると、生成されなかったページが配信先から「削除」として反映される。
```

書いてあったのに、CIがそのファイルを読んでいませんでした。

## 派遣会社の方が読んでいる場合に

このサイトは各社の公開求人を集めて比較しています。お読みいただいている場合に気にされるであろう点を書いておきます。

**サーバーへの負荷**：1社あたり同時接続は1本、リクエスト間隔は1.5秒、毎秒0.65件を超えません。複数社を並行して処理しますが、並行するのは会社をまたぐ場合だけです。この点は実装に錠を掛けて保証しており、実測でも確認しています。

これも最初は守れていませんでした。タスクを350件ずつに刻んで並行実行していたため、**同じ会社のチャンクが同時に最大8本走る**設計になっていたのです。間隔を広げても並行数が増えれば相手から見れば同じことで、1社あたり秒間5リクエストに達しうる状態でした。会社ごとに錠を掛けて直し、実測で確認しています。

```
A社 12件 / 同時接続の最大 1 / 最小間隔 1.55秒
B社  8件 / 同時接続の最大 1 / 最小間隔 1.55秒
```

**掲載する情報**：求人票に書かれている事実（勤務地・職種・時給・寮の種類・食事・勤務期間）だけです。各社が作成された紹介文・キャッチコピー・タグの文言・画像は掲載していません。当初は内部データに各社のタグ表記を保持していましたが、公開ファイルを開けば読める状態だったため廃止し、こちらで判定した結果だけを持つ形に変えました。

**robots.txt**：各社の robots.txt を読んで、Disallow に当たるURLは取得しません。読めなかった場合は「許可されている」とはみなさず、その会社の取得を見送ります。

最後の項目も、最初は嘘でした。派遣会社向けの説明書に「robots.txt を確認しています」と書こうとして、**コードに1行も実装が無い**ことに気づきました。人が目視で確認していただけです。書いた内容と実装が違う状態にはできないので、実装しました。

**求人データを直接ご提供いただける場合**、こちらから貴社サイトへアクセスする必要がなくなります。ご負担がゼロになり、掲載の正確性も上がるため、可能であればその形を希望しています。

## おわりに

1人で作っていると、動いているものを疑う理由がありません。**疑う理由を機械に作らせるしかない**、というのが今のところの結論です。

この記事に書いたバグは全部、直した時点のコミットメッセージに同じ内容を残しています。半年後の自分が同じ穴に落ちたとき、少なくとも「前も落ちた」ことは分かるようにしてあります。
