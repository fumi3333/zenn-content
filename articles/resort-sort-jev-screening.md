リゾートバイトの求人を派遣会社6社から集めて横断比較するサイトを1人で作っています。掲載は約10,000件です。

https://fumiproject.dev/resort/

このサイトには「短期OK」「即日勤務OK」のような、求人ごとの属性を立てる処理があります。この記事は、その判定を最初どう作って、どう壊れていたか、直した先で判定専用モデル（Jev）をどう使ったか、そして求人を集める側として相手サイトへの負荷をどう抑えているかの記録です。

先に結論です。

- ページ全体への文字列マッチで属性を判定すると、ナビや絞り込みUIの文言まで拾って全件Trueになる
- 求人ごとに変わるフィールド（JSON-LDの `description` など）だけを見るように直した
- 属性判定は「文章を生成する」必要がない。判定だけを返すモデル（TypeSafe AI の Jev）に置き換えた
- 判定モデルを使っても、相手サイトに投げるリクエストの数や間隔は変わらない。負荷対策は別に要る

## 何が起きていたか

「短期OK」の判定を、最初はこう書いていました。

```python
def is_short_term_ok(page_html: str) -> bool:
    return "短期" in page_html or "短期歓迎" in page_html
```

求人詳細ページのHTML全体に対して文字列を探しています。動きました。件数も出ました。

それが壊れていたと気づいたのは、実際の値を数えたときです。

```
short_term_ok: 15,501 / 15,501 件（100%）
immediate_ok:  52.9%
```

全件Trueは、さすがに変です。原因はすぐ分かりました。各社ともページの上部や横に「短期」「即日」を含む絞り込みメニューが常設されていて、求人の内容と関係なくその文字列がページに存在していました。**求人ページ全体に対する文字列マッチは、ナビゲーションUIを求人の属性として数えている**のと同じでした。

似たことが期間の判定でも起きていました。ある1社では、`period_raw`（勤務期間の原文）が1,616件すべて「2週間以内」になっていました。これも、絞り込みタブの選択肢のテキストを拾っていたためです。

## 直し方：求人ごとに変わる場所だけを見る

各社の求人ページには JSON-LD（`schema.org/JobPosting`）が埋め込まれています。ここの `description` は求人ごとに書かれた本文で、ナビの文言は含まれません。

```python
def extract_job_description(page_html: str) -> str | None:
    ld_json = _find_jsonld_block(page_html, "JobPosting")
    if ld_json is None:
        return None
    return ld_json.get("description")

def is_short_term_ok(description: str | None) -> bool | None:
    if description is None:
        return None  # 判定できないものは None にする。推測で埋めない
    return bool(re.search(r"短期(歓迎|OK|相談可)", description))
```

判定対象を「ページ全体」から「求人ごとに変わるJSON-LDのdescription」に絞っただけです。特別なことはしていません。ただ、この当たり前を最初に飛ばしていました。

もう一つ実際に事故ったのが、**公開用の `jobs.json` には期間の原文（`period_raw`）を含めていない**ことです。個人情報ではありませんが、原文をそのまま公開すると各社の表記をまるごと転載することになるため、`build_public.py` の段階で外しています。原文で判定したい属性（年末年始限定かどうか、など）は、外す前の内部データの時点で `year_end_only` のような判定済みフィールドとして残しておかないと、あとから「原文を探しても本番には無い」という状態になります。これも一度やりました。

## 判定に生成モデルを使わない理由

正規表現でカバーしきれない表現（「〜まででしたら相談に応じます」のような婉曲な短期可否など）は、そのままだと `None` になります。ここを埋めるのに大規模言語モデルを使うことも考えましたが、この処理でモデルに求めているのは「短期可否・True/False/不明」の3値だけで、文章の生成は要りません。

ここで TypeSafe AI の Jev を使いました。Jev は文章を書かず、型を指定した質問に対して選択・スコア・Yes/No確率のような構造化した判定結果だけを返すモデルです（[gihyo.jp の記事](https://gihyo.jp/article/2026/09/jev-early-access)、[公式サイト](https://jevtypesafeai.com/ja)）。

```python
result = jev.choice(
    context=description,
    question="この求人は短期勤務者を受け入れているか",
    options=["受け入れる", "受け入れない", "記載からは判断できない"],
)
if result.confidence < 0.7:
    short_term_ok = None  # 自信度が低いものは判定を保留する
else:
    short_term_ok = result.choice == "受け入れる"
```

通常のLLMで同じことをやると、生成そのもの（トークンを1つずつ出力する処理）にコストと時間がかかります。判定だけでよいところに文章生成のコストを払っていたことになります。Jevはここを判定に特化させているぶん、同じ処理を安く速く回せます。1万件を超える求人を毎日巡回のたびに判定し直す使い方には、この特化がそのまま効きます。

正規表現でカバーできる大半のケースはそのまま正規表現で判定し、正規表現がNoneを返したケースだけをJevに渡す、という二段構えにしています。全件をモデルに通す必要はありません。

## ここで注意したこと：判定モデルは、相手サイトへの負荷とは別の話

判定モデルを導入する話をすると、「相手サイトに優しくなった」という印象を持たれることがありますが、これは別の話です。Jevが速く安く判定できるのは、**こちらが既に取得し終えたHTML（JSON-LDのdescription）に対して**であって、相手サイトへ投げるHTTPリクエストの数や間隔とは無関係です。

このサイトの巡回設計では、そちらは別に守っています。

- 1社あたり同時接続は1本、リクエスト間隔は1.5秒、毎秒0.65件を超えない
- 複数社を並行して処理する場合も、並行するのは会社をまたぐときだけで、同じ会社への同時接続は増やさない
- 各社の `robots.txt` を読み、`Disallow` に当たるURLは取得しない。`robots.txt` 自体が読めなかった場合も「許可されている」とはみなさず、その会社の取得を見送る

これは実装当初は守れていませんでした。タスクを350件ずつのチャンクに刻んで並行実行していたため、同じ会社のチャンクが最大8本同時に走る設計になっており、間隔を守っていても並行数が増えれば相手から見た負荷は同じでした。会社ごとにロックを掛けて直し、実測で確認しています。

```
A社 12件 / 同時接続の最大 1 / 最小間隔 1.55秒
B社  8件  / 同時接続の最大 1 / 最小間隔 1.55秒
```

判定モデルをどれだけ速くしても、この部分は速くしません。取得の間隔を詰める理由にはならないので、意図的に分けて設計しています。

## まとめ

- 「求人ごとに変わる場所だけを見る」は当たり前ですが、最初に書いたコードはページ全体を見ていて、全件Trueという分かりやすい壊れ方をして気づきました
- 判定だけでよい処理に、文章生成モデルのコストを払う必要はありません。判定専用のモデルに置き換えると、同じ処理を安く速く、大量の求人に対して毎日回せます
- 判定モデルの速さと、相手サイトへの負荷は別の設計です。混同すると「賢くなったから負荷も減った」という誤った説明になります
