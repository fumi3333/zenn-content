リゾートバイトの求人を派遣会社6社から集めて横断比較するサイトを作っています。掲載は12,864件です。

このサイトには、会社をまたいで「同じような求人」を突き合わせ、時給差を抽出する処理が入っています。そこに FlyHash——ショウジョウバエの嗅覚回路を模した局所性鋭敏型ハッシュ——を使いました。実装は229行、抽出できたのは85,377ペアです。

そして本番に載せたあと、**今のデータでは FlyHash である必要がなかった**ことに気づきました。この記事は、なぜ使ったのか、なぜ要らなかったのか、どういう条件なら効いてくるのかの記録です。

先に結論です。

- FlyHash は「似た入力を、似たハッシュ値に落とす」という普通のハッシュ関数と逆の性質を持つ
- 生体の回路構造（まばらな結合・高次元展開・上位数%だけ発火）が、そのまま計算量の節約になっている
- ただし**素性の表現力が足りないと、ただの辞書引きと変わらない**。私の場合がこれだった
- 効いてくるのは、表記揺れのある自由テキストを素性に入れられるとき

## 解きたかった問題

派遣会社は、勤務先の施設名をほとんど公開していません。求人票に出てくるのは「北海道／ニセコ／調理補助」くらいの粒度です。契約上の事情で伏せているのだと思います。

そのため、A社の求人とB社の求人が同じ現場なのかを、文字列一致で判定できません。表記も揃っていません。「賀茂郡河津町」と書く会社もあれば「河津」と書く会社もあります。

さらに、全件総当たりだと 12,864 の2乗でおよそ8,300万通りです。素朴に回すと時間がかかります。

「似ているものを高速に集める」問題なので、近似最近傍探索の出番です。ここで FlyHash を選びました。

## キノコ体がやっていること

ショウジョウバエは数千種類の匂いを嗅ぎ分けます。その処理を担うキノコ体（Mushroom Body）は、構造がかなり変わっています。

入力側の射影ニューロン（PN）は数十次元しかないのに、その先のケニオン細胞（KC）は2,000個以上あります。**情報を圧縮せず、いったん高次元に広げます。** そして各KCは、全PNの中からランダムに数本だけ枝を伸ばして結合しています。最後に APL という抑制性ニューロンが全体を見張り、強く反応した上位数%のKCだけを残して、他を黙らせます。

結果として、1つの匂いは「2,000個のうち100個くらいだけが光っているパターン」になります。似た匂いは似たパターンに、違う匂いは重ならないパターンになります。

これをアルゴリズムとして定式化したのが FlyHash です（Dasgupta, Stevens, Navlakha, *Science*, 2017）。

普通のハッシュ関数は、入力が1ビット違えば全く違う値を返すように設計されています。FlyHash はその逆で、**似た入力を意図的に似た値に落とします。** だからハッシュ値同士の距離を測ることに意味が出ます。

面白いのは、次元削減の定番である Johnson–Lindenstrauss の補題が「ランダム射影は距離をおおむね保つ」ことを保証しているのに対し、FlyHash は**次元を増やす**方向のランダム射影を使う点です。増やしたうえで上位数%に絞るので、最終的な表現は疎な二値ベクトルになります。

## 実装

求人1件を、こういう素性の集合に変換します。

```python
def extract_features(job):
    tokens = []
    if job.get("prefecture"):   tokens.append(f"pref:{job['prefecture']}")
    if job.get("city"):         tokens.append(f"city:{job['city']}")
    if job.get("job_category"): tokens.append(f"cat:{job['job_category']}")

    text = f"{job.get('workplace_name') or ''} {job.get('city') or ''}"
    clean = re.sub(r"[【】\[\]\s★♪◆◇◎※・\-_/0-9]", "", text)
    for i in range(len(clean) - 2):
        tokens.append(f"ng3:{clean[i:i+3]}")   # 3文字ずつの部分文字列
    return tokens
```

全件を通すと、語彙は **7,588種類** になりました。これが PN 層の次元数です。

ここから先が回路の再現です。

```python
class FlyConnectomeEngine:
    def __init__(self, n_kc=2048, syn_per_kc=6, top_k_ratio=0.05):
        self.n_kc = n_kc                              # KC層のニューロン数
        self.syn_per_kc = syn_per_kc                  # 各KCが伸ばす枝の本数
        self.top_k = max(1, int(n_kc * top_k_ratio))  # 発火させる数（上位5%）
```

- `n_kc=2048`：7,588次元の入力を、2,048個のKCに投げます
- `syn_per_kc=6`：各KCは7,588個の入力から**6本だけ**結合します。重みは対数正規分布から引きます
- `top_k_ratio=0.05`：反応が強かった上位5%（102個）だけを1、残りを0にします

結合行列は疎行列で持ちます。2,048 × 6 = 12,288 本しかないので、密行列の **0.08%** です。生体のまばらな結合が、そのまま計算量とメモリの節約になっています。

```python
from scipy.sparse import csr_matrix
self.weights = csr_matrix((data, (rows, cols)),
                          shape=(self.n_kc, n_pn), dtype=np.float32)
```

エンコードは、疎行列との積を取って上位k個を立てるだけです。

```python
act = self.weights.dot(x)
thresh = np.argpartition(act, -self.top_k)[-self.top_k]
hashes.append((act >= act[thresh]) & (act > 0))
```

`np.argpartition` はソートせずにk番目の値を求めるので O(n) です。2,048個を毎回ソートすると効いてきます。

比較は XOR を取って立っているビットを数えるだけです。

```python
dist = int(np.sum(hashes[a] ^ hashes[b]))
if dist <= max_hamming:
    ...
```

乱数シードは固定します（`np.random.seed(42)`）。結合がランダムなので、固定しないと実行のたびに結果が変わります。

## ここまでは動いた。そして要らなかった

抽出できたペアを実際に開いてみました。

```
距離5  北海道定山渓／洗い場    A社 1,300円  vs  B社 1,120円
距離8  北海道ニセコ／調理補助  A社 1,500円  vs  B社 1,200円
距離6  長野県白馬／ホール      B社 1,400円  vs  A社 1,100円
```

それらしく見えます。でも `extract_features` を読み返すと、効いているのは**都道府県・市区町村・職種と、市区町村名の3-gram**だけです。施設名はほとんどのデータに入っていないので、`text` の中身は実質 `city` しかありません。

つまり3-gram は市区町村名を刻んでいるだけで、`city:` の素性と情報がほぼ重複しています。**素性が実質3つしかない状態でハッシュを作っていたことになります。**

そうなると、これで判定できるのは「同じ市区町村の同じ職種」までです。定山渓には宿が何十軒もあるので、距離5で一致した2件が同じ旅館とは限りません。

そして素性が3つなら、こう書けば終わりです。

```python
from collections import defaultdict
buckets = defaultdict(list)
for j in jobs:
    buckets[(j["prefecture"], j["city"], j["job_category"])].append(j)
```

FlyHash が必要ありません。しかも辞書引きのほうが速く、結果も厳密です。

## どこで判断を間違えたか

「表記揺れがあるから近似マッチが要る」と考えたところまでは合っていました。間違えたのは、**表記揺れがある対象（施設名）のデータを、そもそも持っていなかった**ことです。

持っていないデータの揺れを吸収するアルゴリズムを入れても、吸収するものがありません。素性を並べた時点で気づけたはずでした。

「アルゴリズムを選ぶ前に、そのアルゴリズムが効く入力が手元にあるか数えろ」という、字にすると当たり前の話です。私は先に実装を書いてしまいました。

## どういう条件なら効くのか

FlyHash が報われるのは、次のような場合だと考えています。

**素性が高次元で疎なとき。** 文書の bag-of-words や n-gram のように、語彙が数千〜数万あって、1件あたりに立つのは数十というデータです。今回の私のように実質3次元だと、高次元に展開する意味がありません。

**候補集合を絞り込みたいとき。** ハミング距離はビット演算なので、ペアあたりのコストが極端に小さくなります。厳密な判定を後段に置いて、その前段のふるいとして使う形が噛み合います。

**逐次的にデータが増えるとき。** 結合行列はランダムに作るだけで、学習が要りません。新しい求人が来てもモデルを作り直す必要がなく、その場でエンコードできます。学習済みの埋め込みモデルと比べたときの実務的な利点はここだと思います。

私の場合、施設名の取得率を上げれば1つ目と2つ目の条件が揃います。各社のJSON-LDには郵便番号と番地が入っていることがあるので、そちらを素性に足すのが次の課題です。実際、住所が一致するものだけを厳密に突き合わせる処理も別に書いていて、そちらは15か所しか見つかりません。85,377と15。この差が、そのまま手法の緩さの差です。

## 想定される指摘

**「精度は測ったの？」**

測っていません。閾値は出力を眺めて決めた値です。正解データを作っていないので、「精度◯%」と書ける状態にありません。書けないので書いていません。

**「MinHash や SimHash ではだめなの？」**

だめではないです。集合の類似度なら MinHash のほうが素直ですし、実装も枯れています。FlyHash を選んだのは、疎な入力に対して学習なしで使えることと、単純に構造が面白かったからです。後者は正直な動機なので書いておきます。

**「2,048 や 6 という数字はどう決めたの？」**

元論文の設定に寄せました。生体のキノコ体はKCが約2,000個、各KCの入力が平均6本程度とされていて、そこをそのまま使っています。チューニングの余地はありますが、精度を測っていない以上、いじっても良し悪しを判断できません。

## まとめ

生体の回路をそのまま計算に持ってくる話は、読んでいて面白いし、実装も難しくありません。229行で動きます。

ただ、**面白さと、それが自分の問題に必要かどうかは別**でした。素性を3つしか作れていないのにハッシュを設計していた、というのが今回の実態です。

同じことをやろうとしている人がいたら、実装の前に `extract_features` 相当の関数だけ書いて、語彙数と1件あたりの素性数を数えてみてください。そこで答えが出ます。
